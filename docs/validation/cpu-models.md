# 실제 CPU 모델 검증 · v0.6.2 관측

2026-10-18, CPU 8코어 할당 / 메모리 제한 8GiB 환경에서 두 모델의 실제 가중치를 사용했다. 모델 대역을 사용한 회귀 검사와 구분한다. 모델을 각각 별도 프로세스로 로드하고 CPU float32·4스레드로 실행했다. 실제 사용자 GPU 서버에 접속해 추론한 결과는 아니다.

## 모델과 입력

| 모델 | 고정 revision | 가중치 SHA256 |
| --- | --- | --- |
| RF-DETR Seg 2XL 1152 | `aed55fdb8ca953c6bec33cf6ed6dd52a9b72bfa2` | `9bf6d2cbd7793c956d8c857bb1672a396eb7f100eb0682f86830d05e31168efb` |
| Hayai OCR v2 | `4a4ce477c9a8841f208b94e1d9ed5c0938965e05` | `4c645b221db8428cda04991be234c18133bb8861142a3d87cba04c5099b02328` |

가중치뿐 아니라 실행되는 모델 코드·설정·토크나이저도 프로젝트의 고정 SHA256과 대조했다. 네트워크 다운로드 후 실제 추론에는 `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1`을 사용했다. 모델 이름·출처는 기존 adapters의 metadata에 있다.

입력은 사용자가 첨부한 1280×1815px 이미지다. 주황색 검수 박스가 실제 픽셀에 포함되어 있으므로 사용자 서버의 박스 없는 원본과 동일한 입력이라고 부르지 않는다. 입력 파일 SHA256은 `fca1e909af81eb8cee6b75602bd5b5f594d9ca4f796675e9e59967b4c4aac91c`다. 사용자 이미지·개별 크롭은 공개 Git에 넣지 않는다.

환경은 torch 2.6.0+cpu, torchvision 0.21.0+cpu, transformers 5.1.0, rfdetr 1.7.0, tokenizers 0.22.2, supervision 0.27.0이다. 원래 로더가 동적으로 만든 모듈을 등록하지 않아 Transformers 5.1의 클래스 조사에서 실패하는 문제도 발견했다. 로더를 `sys.modules`에 등록한 뒤 실제 가중치 로드와 추론이 성공했다. 가중치·생성 알고리즘은 변경하지 않았다. 운영 노드의 CUDA 필수 정책도 유지한다.

## 검출 6조건

전체 페이지, 기존 복구와 같은 `[0,410,1152,1562]` 문맥, `[50,943,662,1164]` 크롭, 흰 페이지를 기본 임계값(text .25 / onomatopoeia .20 / bubble·panel .50)으로 실행했다. 추가로 전체 페이지와 문맥만 text·onomatopoeia .10에서 진단했다. 모델 입력은 기존 어댑터의 1152×1152다.

| 조건 | text | onomatopoeia | 추론 시간 |
| --- | ---: | ---: | ---: |
| 전체 페이지 / 기본값 | 0 | 2 | 18.681s |
| 1152 정사각 문맥 / 기본값 | 0 | 6 | 17.604s |
| 기존 OCR 크롭 / 기본값 | 0 | 2 | 13.089s |
| 흰 페이지 / 기본값 | 0 | 0 | 13.018s |
| 전체 페이지 / .10 진단 | 18 | 20 | 19.381s |
| 정사각 문맥 / .10 진단 | 32 | 22 | 15.516s |

전체 페이지의 프로필 본문 후보 score는 약 .178, 문맥에서는 약 .187이었다. 기본 .25를 넘지 못했다. 낮은 임계값에서 효과음·그림 쪽 후보와 중복 후보도 늘었다. 개수는 고유한 글줄 수나 정답 수가 아니며, 이 자료로 임계값을 일괄 낮추는 결론을 내리지 않는다. 최고 RSS는 약 3.25GiB였다.

GPU 보고서와 CPU의 검출 수·좌표는 완전히 같지 않다. 박스 주석, 라이브러리 버전, float32와 GPU의 연산 차이를 분리하지 않았으므로 CPU/GPU 동등성이나 동일 원인 재현을 주장하지 않는다.

## OCR 19케이스

18개 입력·설정 조합과 같은 15px 조각의 동일 조건 재실행 1건이다. 독립적인 이미지 19장이나 정답 19개를 뜻하지 않는다.

기존 612×221px 크롭, -13.5° 회전한 648×359px 전체, 더 넓은 크롭을 회전한 845×519px 전체, 기존 자동 계획 6행, 높이 15px 조각, 수동으로 온전한 글줄을 남긴 4개 대조 크롭, 512/1024 패치 비교를 수행했다. greedy / repetition_penalty=1.0 / max_new_tokens=256을 유지했다. 수동 대조 크롭은 진단용이며 자동 워크플로우가 이 영역을 찾았다는 뜻은 아니다.

| 조건 | 실제 응답의 예 | 관측 |
| --- | --- | --- |
| 원래 전체 크롭 / 256 | `MY PROBLE … サーバーのサーバ …` | 긴 오독 재현 |
| 기존 자동 계획 0행 | `MY PROFILE` | 제목 인식 |
| 기존 자동 계획 1행 | `(わたし)の名前はカーマ!` | 이름 문장은 개선되나 일부 문자 누락 |
| 기존 자동 계획 2행 | `クラスはアサシンのサーヴァントなんだ☆` | 이 글줄은 읽음 |
| 기존 자동 계획 3행 | `<UNK_SPAN>` | 미인식 재현 |
| 기존 15px 조각 / 512 | `⇒\|eRuster Dr.Oirk)` | 잘린 글자 입력의 오독 |
| 온전한 해당 글줄 / 512 | `宝貝(Buster-Art-Quick)` | 읽기가 개선되나 宝具·Arts 오독 잔존 |
| 같은 온전한 글줄 / 1024 | `豆Bster At Quc Quc` | 패치 증가가 개선을 보장하지 않음 |
| 넓은 전체 크롭 / 1024 | 반복되는 `/4/4/…` | 반복 검사로 거부 |

입력과 행 경계를 육안으로 확인했다. 기존 직사각 크롭은 아래쪽 문장의 일부를 이미 잘랐고, 행 계획의 231·246px 경계는 실제 `Buster·Arts·Quick` 글줄을 가로질렀다. 빈 무늬에 가까운 부분을 별도 행으로 인식한 것도 확인했다. 원래 크롭에 없는 획은 회전이나 패치 증가로 복원할 수 없다. 반대로 온전한 행에도 잔여 오독이 있어, 전처리만 고치면 모든 글자가 맞는다고 주장하지 않는다.

OCR의 `issue=null`은 현재 반복·누락·명시적 미인식 표시 검사에 걸리지 않았다는 뜻이다. 글자를 정확히 읽었다는 신뢰도가 아니다. 정답 전사를 독립적으로 확정하지 않아 CER/WER·정확도 백분율은 산출하지 않는다. 추론 시간과 메모리는 실행 JSON에 남겼으며 DGX 성능 추정에 사용하지 않는다.

## 확인한 계약 결함과 수정

첨부 OCR 보고서에서는 첫 `<UNK_SPAN>`을 감지한 뒤 레이아웃 복구에서 `<UNK><UNK>`를 정상으로 통과시켰다. 이제 `<UNK>`·`<UNK_SPAN>`·`[UNK]`의 대소문자 변형을 공통 검사하고, 모든 복구 조각·합친 결과·번역 입력·번역 출력·식자에서 같은 계약을 적용한다. 표시를 지워서 성공으로 처리하지 않는다.

첨부 번역은 원문의 개행을 새 `{n}`으로 바꿨다. 원문에 개행이 있고 `{n}`은 없는데 응답에 새로 생기면 한 번 재생성을 요청한다. 해결되지 않으면 실패 응답을 저장하고 중단한다. 임의 템플릿 문자열을 개행으로 추측 변환하지 않으며, 원문에 실제 있는 `{n}`과 검수한 수동 override는 보존한다. v0.6.1의 좁은 `<br>` 정규화는 유지한다.

## 재현 도구와 남은 작업

`tools/validate_cpu_models.py`는 ComfyUI를 시작하지 않는 명시적 CPU 진단 도구다. 모델별로 별도 프로세스에서 실행한다. cases JSON은 `[{"id":"case1","image":"input.png","patches":512}]` 형태다. 검출 진단에는 선택적으로 네 라벨의 `thresholds`를 지정한다. 출력에는 입력 SHA256·모델 revision·버전·실제 응답·토큰 수·시간·RSS가 포함된다. 실패한 출력도 원문 그대로 보존한다.

```bash
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 python tools/validate_cpu_models.py \
  --kind ocr --model-root /path/to/diagnostic-models \
  --cases /path/to/cases.json --output /path/to/ocr-results.json --threads 4
```

`model-root/hayai`와 `model-root/detector`에 해당 고정 bundle을 둔다. 검출은 `--kind detector`를 사용한다. 이 도구를 위해 운영 ComfyUI의 torch를 CPU 버전으로 교체하지 않는다.

이번 검증의 결론은 **검출 후보 선택·크롭/행 분할의 결함과 이 이미지 조건에서의 모델 인식 한계가 함께 존재한다**는 것이다. 이 기록 이후의 글줄·원본 문맥 복구는 [후속 v0.6.4 검증](source-context.md)에 있다. 현재 적용 방법은 [사용법](../usage.md)을 따른다. 이 관측만으로 일반 인식 정확도나 GPU 성능을 판단하지 않는다.


## v0.7.0 선택 OCR · 실제 CPU 확인

2026-10-18, `kha-white/manga-ocr-base` revision `aa6573bd10b0d446cbf622e29c3e084914df9741`의 6개 파일 SHA256을 확인해 내려받고 새 어댑터를 CPU에서 실행했습니다. torch 2.14.1+cpu, Transformers 5.1.0, 4스레드, greedy, 최대 256토큰 조건입니다. 가중치는 444,135,475 bytes이며 모델 입력은 224×224입니다. 사용자 운영 torch/CUDA를 교체한 결과가 아닙니다.

[원본 문맥 복구 관측](source-context.md)의 같은 첨부 이미지에서 문맥 `[0,807,798,1300]`을 -13.5도로 회전한 뒤 고정한 5개 행 크롭을 사용했습니다. 이번 실행에서 검출/Hayai를 다시 돌린 것은 아니며, 검출부터 자동 선택한 전체 파이프라인 평가와 구별합니다. 주황 주석이 있는 입력 이미지라는 한계도 같습니다.

| 행 / 크기 | Manga OCR 실제 응답 |
| --- | --- |
| 제목 · 272×78 | `MYPRのPLEC` |
| 이름 · 500×36 | `わたしぼくの名前は、カーマート` |

이번 5개 행에서는 기존 Hayai 관측보다 좋아졌다고 볼 수 없습니다. 제목의 라틴 문자, 혼합 표기, 손글씨의 오독이 남았습니다. 넓은 문맥 전체를 한 번에 넣은 별도 조건에서도 원문과 다른 문장을 생성했습니다. 그래서 엔진을 자동으로 더 정확하다고 판단하거나 두 결과의 일치만으로 승인하지 않습니다.

같은 이름 행으로 실제 `MangaOCRAdaptiveCached`를 두 번 실행해 첫 실행 computed, 두 번째 reused와 동일 텍스트를 확인했습니다. 개별 행 직접 추론은 모델 로딩 후 약 0.35–0.44초였지만 일반 CPU 성능이나 GPU 속도 수치로 쓰지 않습니다. 모델 로딩에서 position_ids의 unexpected key 및 기존 generation flag 경고가 있었으며, 숨기기 위해 체크포인트/설정을 수정하지 않았습니다. Qwen·실제 번역 서버까지의 GPU 전체 품질 평가는 아닙니다.
