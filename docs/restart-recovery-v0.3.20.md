# v0.3.20 재시작으로 남은 실행 중 시도 복구

실제 보고에서는 첫 페이지의 `attempt-000003`이 2026-10-17 22:47:39 KST에 생성되고 22:47:50에 갱신된 뒤 `running`으로 남았다. 재시작 후에는 큐가 비었고, 22:48:46에 시작한 폴더 부모 prompt의 성공 이력만 남았다. 이전 페이지 작업의 결과는 확인할 수 없었다.

기존 실행기는 미확정 작업의 중복 제출을 막기 위해 계속 일시정지했다. `실패 재시도`를 선택해도 active 시도부터 먼저 복구하므로, 재시작으로 사라진 작업을 워크플로우 안에서 정리할 수 없었다.

## 같은 워크플로우에서 복구

업데이트 후 ComfyUI를 재시작하고, 같은 통합 08 입력 노드에서 같은 프로젝트 이름과 `action=실패 재시도`로 실행한다. 새 복구용 워크플로우·사이드바·수동 state 편집은 필요 없다.

다음 조건이 모두 충족된 경우에만 이전 시도를 정리한다.

1. 사용자가 명시적으로 `실패 재시도`를 선택했다.
2. 현재 ComfyUI의 실제 OS 프로세스 생성 시각을 확인했다.
3. 이전 시도의 생성·갱신 시각이 현재 프로세스보다 앞선다. 초 단위 저장 오차를 피하기 위해 2초 여유를 둔다. 새 버전이 기록한 프로세스 정보가 있으면 같은 프로세스나 더 새로운 프로세스의 기록은 복구 대상으로 인정하지 않는다.
4. 기존 prompt ID와 프로젝트/페이지/시도 토큰이 실행·대기 큐에 없고, 원래 prompt 이력도 없다. 연속된 확인 뒤 정리 직전 다시 확인한다.
5. 사용자가 일시정지를 요청하지 않았다.

이전 시도는 `failed / server_restarted_outcome_lost`로 기록한다. 이는 모델 실행이 실패했다고 확정하는 의미가 아니라, 재시작으로 결과 확인이 불가능해졌다는 뜻이다. 이전 prompt ID·토큰·원본 입력·부분 결과는 보존하고 재시작 확인 근거도 기록한다. 이후 새로운 attempt와 prompt ID로 같은 페이지를 제출한다. 보고된 세 번째 시도는 보존되고 네 번째 시도로 진행한다.

새 제출에는 ComfyUI 프로세스 생성 시각과 PID도 기록한다. 모듈을 다시 import한 시각을 서버 재시작으로 간주하지 않는다. 프로세스 생성 시각은 ComfyUI의 기존 `psutil` 의존성으로 읽으며 확인이 불가능하면 복구하지 않는다.

## 계속 유지하는 중단 조건

- `시작·재개`는 미확정 시도를 정리하거나 자동 재제출하지 않는다.
- 같은 프로세스에서 이력만 사라진 작업, 시각이 없거나 모순된 기록, 실제 큐에 있는 작업은 계속 정지 또는 대기한다.
- HTTP 실행기는 원격 프로세스의 시작을 증명하지 못하므로 이 복구를 적용하지 않는다.
- 완료 이력이 있으면 기존 결과를 수집하고 새 실행을 제출하지 않는다. 마지막 확인 순간 이력이나 큐에 나타난 작업도 정리하지 않는다.
- 다른 프로젝트나 사용자의 작업을 취소하거나 큐를 비우지 않는다.
- 이미 완료된 페이지는 재실행하지 않는다. 제거된 원본은 남은 시도 기록을 정리하더라도 다시 제출하지 않는다.

기존 페이지의 실제 OCR/검출/식자 예외는 새 실행 결과에서 확인해야 한다. v0.3.19의 실제 오류 보존과 자원·설정·원인 불명 오류 중단 정책은 그대로 적용한다.

## 검증

`tests/test_restart_recovery.py`는 보고된 UTC 시각과 세 번째 시도를 재현한다. 네 번째 시도로의 전환, 이전 두 시도와 입력 보존, 일반 재개 차단, 같은 프로세스·시각 오류·프로세스 정보 부재, 살아 있는 큐·완료 이력·최종 확인 시점의 경쟁, HTTP 경로·일시정지·제거된 원본을 검사한다. 실제 DGX 모델 추론은 이 검증에 포함하지 않는다.
