# 번역 응답 계약 v0.5.1

실제 v0.5.0 보고서는 completed 10 / needs_review 5 / unchanged_blank 2 / failed 1이다. 11_11.jpg의 실패는 MangaTranslate에서 JSON 파싱이 두 번 실패한 것이다. 마지막 응답은 stop / 141 completion tokens / 304 characters였고 1행 247열에서 파싱되지 않았다. 실제 응답 원문이 없어 따옴표·개행·조기 종료 중 무엇인지 확정할 수 없다. 이 정보만으로 토큰 한도 부족이라고 판단하지 않는다.

## 출력 프로토콜

번역 노드의 optional `response_format`은 기본 `json_schema`다. 표준 OpenAI 호환 요청의 response_format.json_schema에 페이지의 요청 ID 목록, 정확한 항목 개수, id/target 필수 필드, 추가 필드 금지를 보낸다. vLLM 공식 [Structured Outputs](https://docs.vllm.ai/en/stable/features/structured_outputs/)의 요청 형식을 따른다. 원본 보존이 확인된 점 나열은 생성 대상과 스키마에서 제외한다. 기존 JSON 파서와 ID 중복·누락·대상 문자 길이 검증은 서버 제약과 별도로 유지한다. 잘못된 JSON을 임의로 고치거나 일부 번역만 채택하지 않는다.

JSON/영역 계약 실패만 기존처럼 한 번 다시 요청한다. 비정상 종료, 빈 답변, HTTP/연결 오류는 별도로 중단한다. API가 스키마 모드를 거부하면 자동으로 제약을 해제하지 않는다. 서버 기능을 확인한 뒤 `json_object`(JSON 문법 제약) 또는 `prompt_only`(기존 프롬프트 요청)를 직접 선택할 수 있다. 이 명시적 모드 변경은 프로젝트 처리 설정 변경으로 간주한다. 서버 버전·스키마 백엔드·모델의 실제 지원 여부는 사용자 환경에서 확인해야 한다.

## 진단

번역 생성 요청이나 응답 검증에서 끝내 실패하면 output/manga_translator/translation_failures/translation_<id>.json에 요청 원문 영역, 선택한 모델/언어/한도/모드, 각 실패 응답의 content, finish_reason, completion_tokens, 파싱/계약 오류를 저장한다. 답변은 시도당 최대 200,000자로 제한하고 잘림 여부를 표시한다. 헤더·API 키·서버 URL·reasoning 필드는 저장하지 않는다. 콘솔에는 원문 답변 대신 진단 파일 위치를 남긴다. 진단 저장 실패는 원래 번역 오류를 대체하지 않는다.

## 기존 프로젝트 재시도

v0.5.0 → v0.5.1의 기본 모드 추가는 프로젝트 fingerprint에 영향을 주지 않도록 정규화했다. 코드를 업데이트하고 ComfyUI를 재시작한 뒤 기존 캔버스·project_name에서 `실패 재시도`를 실행한다. JSON을 다시 가져오거나 새 프로젝트를 만들 필요는 없다. 새 예제에는 모드 위젯이 저장되어 있다. 기존 캔버스에서 새 위젯이 보이지 않아도 생략된 optional 입력의 실행 기본값은 json_schema다.

현재 보고서에서 이 동작은 failed 상태인 11_11.jpg만 다시 처리한다. 검수 상태 5페이지는 자동 재시도하지 않는다. 04/08/09는 미복구 검출 경계 보존, 02는 미검출·빈 페이지 미확정, 18은 제외된 효과음이 이유다. 이 릴리스가 이 다섯 이유나 번역 의미 정확도를 해결한 것은 아니다.

## 검증 범위

모의 HTTP 요청의 실제 JSON 전송, 요청 ID 스키마, 여전히 필요한 클라이언트 검사, 한 번의 재시도, 명시적 호환 모드, HTTP 거부 시 자동 강등 금지, 두 실제 응답 보관, 큰 응답 제한, 자격 정보 제외, 진단 저장 실패를 검사한다. v0.5.0 그래프에서 완료 1장/번역 실패 1장을 만든 뒤 새 기본 그래프로 같은 프로젝트의 실패 페이지만 선택하는 네이티브 캔버스 회귀를 검사한다. 실제 사용자 vLLM 서버나 해당 18페이지 GPU 재실행 결과는 포함하지 않는다.
