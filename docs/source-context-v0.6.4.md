# v0.6.4 원본 문맥에서 잘린 글줄 복구

v0.6.3의 `source_crop_cuts_glyphs`는 OCR·번역을 생략하고 원본을 남겼다. 이 동작은 잘못된 원문을 번역하는 문제를 차단했지만, 이미지를 번역하지 못한 원인은 그대로였다. v0.6.4는 그 보존 처리 **앞**에 원본 문맥 복구를 추가한다.

## 처리 계약

- 기존 검출 마스크에서 회전각과 여러 기준선이 관측되고, RGB 글자 성분에서 크롭 잘림을 발견한 경우에만 복구한다. 새로운 검출 클래스·문장 의미·번역 내용을 추측하지 않는다.
- 글자 높이의 4배, 최대 192px의 주변 원본을 한 번 읽는다. 분석 원본 4 Mi 픽셀·회전 래스터 8 Mi 픽셀, 성분 32768·행 32개·행의 작은 성분 2048개 한도를 유지한다. 확대 재시도 루프는 없다.
- 원래 각 기준선에 대응하는 문맥 기준선이 하나여야 한다. 같은 높이·기준선의 연결 성분과 가까운 구두점을 포함한다. 별도 Skill 문단 같은 새로운 행은 자동 편입하지 않는다. 여전히 잘린 글자, 모호한 행, 다른 선택/보존 영역의 편집 범위와 중첩하면 복구하지 않는다.
- 복구한 OCR은 넓은 문맥 사각형 전체를 읽지 않고, 회전한 좌표계의 각 글줄 사각형을 읽는다. 원본 검출 bbox는 `source_detection_bbox`로 남기고, 최종 bbox·행 bbox·crop/edit bbox는 복구한 원문과 같은 페이지 좌표를 사용한다.
- 제거 단계는 원본 RGB와 동일한 글줄 기하에서 작은 글자 성분 마스크를 다시 계산한다. 임의의 제거 비트맵이나 넓어진 사각형 전체를 지울 권한으로 쓰지 않는다. 페이지 픽셀 해시·행 해시·마스크 외곽·편집 영역을 확인하며, 원본이 달라지면 제거 전에 거부한다. 같은 각도는 식자에도 전달된다.
- 복구 실패 시 기본 `preserve_review`는 원본 보존과 `needs_review`를 유지한다. `strict`는 복구가 실패한 시점에 중단한다. OCR의 미인식·반복·토큰·누락 검사는 그대로 유지하며 기하 복구 성공이 인식 정확도 보증은 아니다.

## 실제 입력 확인

사용자가 제공한 1280×1815px 이미지와 이전 실제 CPU 검출 마스크의 원래 크롭 범위 안의 지지 픽셀을 사용했다. 사용자의 GPU 마스크 자체를 전달받은 것은 아니다. 첨부 이미지에 주황 검수 사각형이 실제로 들어 있으므로 주석 없는 원본·GPU 실행과의 동일성을 주장하지 않는다.

기존 OCR 크롭 `[50,943,662,1164]`에 대해 문맥 `[0,807,798,1300]`에서 원래 5개 기준선의 글줄을 구성했다. 아래 두 글줄의 빠진 획을 포함하며, 오른쪽 인물 사진과 아래 Skill 문단은 OCR 행에서 제외됐다. 복구한 입력 5개를 고정 revision/SHA256의 Hayai v2, CPU float32·4스레드·greedy·256패치·256토큰으로 직접 추론했다.

| 행 | 실제 응답 |
| --- | --- |
| 제목 | `MY PROFILE` |
| 이름 | `(わたし・ぼく)の名前はカーマ` |
| 클래스 | `クラスはアサシンのサーヴァントなんだ☆` |
| 이전 미인식 행 | `宝具(Buster・Arts·Quick)` |
| 아래 손글씨 | `愛もてかれるは恋無きなり` |

이름의 끝 구두점 누락과 손글씨 오독 가능성은 남는다. 품질 검사 `issue=null`은 정답 보증이 아니다. 전체 페이지의 미검출된 글자나 효과음 제외 문제가 해결됐다는 뜻도 아니다. 번역 서버·Qwen 제거·최종 GPU 식자까지 실제 모델로 실행한 결과는 아니다.

같은 원본·크롭 안에 제한한 실제 CPU 검출 마스크를 `MangaRegionCrops → MangaOCRAdaptive → MangaCollectOCR`에 넣어 실제 Hayai를 호출하는 통합 경로도 별도로 실행했다. 작은 행에 기본 512패치를 쓰는 이 경로의 원문은 아래와 같다. 256패치 직접 추론보다 이름·클래스에서 오독이 늘었으며, 패치 수를 올리는 것이 정확도 향상을 보장하지 않음을 다시 확인했다. 5행 모두 실행됐고 `ocr_skipped`로 우회하지 않았다.

```text
MY PROFILE
(わたし・ぼくの名前はカーマー!
クラスはアサシのサーヴァントなんだ☆
宝具(Buster·Arts·Quick)
愛もてかれるは恋無きなり
```

이 실행에서 검출 지지가 약한 왼쪽 손글씨를 누락시키는 초기 복구 구현도 발견했다. 같은 기준선·높이의 이어지는 묶음이 검출 크롭 밖에 있다는 이유로 제외되지 않도록 수정한 뒤 재실행했다. 실제 최종 행은 178px 일부가 아니라 424×50px 전체 입력이었다.

## 적용과 확인 위치

`git pull` 후 ComfyUI를 재시작하고 브라우저를 새로고침한다. 기존 통합 08의 `auto_deskew=true` 경로에도 적용되며, 새 08의 노드 제목은 `④ OCR 전 단·회전 보정 · 원본 문맥 복구·검수`다. 처리 입력과 연결은 유지하므로 새 프로젝트 이름을 요구하지 않는다.

이미지 한 장 모드는 다시 Run한다. 폴더에서는 현재 보존 결과가 `needs_review`이므로 기존 **실패 재시도**로는 선택되지 않는다. 새 **실패·검수 재시도**를 선택하면 failed/needs_review만 새 시도로 처리한다. completed/unchanged_blank는 유지하고 이전 시도 파일은 덮어쓰지 않는다. 재시도한 페이지가 다시 검수가 되어도 같은 실행 안에서 무한 재처리하지 않는다.

기존 `미리보기 아무거나`에서 다음을 확인한다.

- `ocr_geometry_recovery.regions[].status`: `recovered` 또는 `preserved`, 복구/보류 사유와 원래/문맥 bbox.
- `regions[].ocr_region_plan.row_mode`: 복구하면 `context_glyph_bounds`.
- OCR의 `source`: 실제 읽은 원문. 복구가 성공하면 `ocr_skipped`로 우회하지 않는다.
- 편집 계획의 `needs_review`: 상위 검수 상태를 그대로 이어받는다. v0.6.3처럼 상위 true / 편집 계획 false로 엇갈리지 않는다.
